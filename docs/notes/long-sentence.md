# 长句准确率：诊断与头两步（2026-09-19）

起因是一个问题：长句怎么打、拼音准确率怎么提。结论先说：**长句现在就能打**（120 键的句子每键平均 3 ms，没有长度上限），
问题是**越长越错**，而且错在打分，不在搜索。这篇记诊断的数字、做掉的两步、试过不行的和下一步。

## 尺子

- 干净集：`docs/` 51 个文件经 `--eval-text` 抽出 9526 句（3–20 字），冷启动，`--eval-save` 冻结。行话密，绝对数字低，只看相对变化。
- 分段输入：同一份句子 `--eval-chunk 2`，每句按语言模型切词、两个词一段逐段喂，前面各段的原文当上文，22343 段。
- 注错集：同一份句子 `--eval-typos`，每条拼音注一处敲错（相邻键换位 / 敲到旁边的键，按句子哈希定）。
- 真实日志：`--replay` 冻结的 `input-log.jsonl`，11158 行，词 5736 / 整句 283。整句那一栏「选了」多半是旧引擎自己的输出
  （笔给 / 发不 / 并白），只看词级与「现在仍纠」。

## 诊断

| 字数 | 句数 | 整句首选 | 字准确率 | 开本地模型后字准确率 |
|---|---|---|---|---|
| 3–5 | 4053 | 39.4% | 69.8% | 74.8%（+5.0） |
| 6–10 | 3915 | 22.2% | 71.5% | 74.2%（+2.7） |
| 11–15 | 1285 | 10.6% | 72.5% | 74.2%（+1.7） |
| 16–20 | 273 | 8.1% | 75.5% | 76.7%（+1.2） |

- 单字一直 70–77% 对，句子一长全对就难。没命中的 6732 句里 99% 是同长的同音换字（差 1 / 2 / 3 字各占 29% / 28% / 19%），切分错只有 45 句。
- **敲错边误伤干净输入**：关掉敲错边 27.6% → 29.3%、字 71.6% → 73.4%；弄坏 169 句、另改动 1125 句、修好 4 句。
  `anpaiceshirenyuan` 出 安排的是人员：`ce` 被当成敲错的 `de`，的 + 是 的语言模型分盖得过 5 nat 的代价。开着本地模型这笔账还在（32.1% 对 33.8%）。
- **整句不看上文**：`best_predecessor` 起点写死 `Context::START`，词级排序才用上屏链。分段打、先选了前面的词，后半句都当句首算。
- **给神经重排的 k 条路径只在句尾不同**：`convert_paths` 回溯的是 `nodes[n]` 里每个末词各自的最优链。
  模型增益随句长从 +5.0 掉到 +1.2；16–20 字桶 k 从 6 加到 24（束宽 32）76.7% → 76.8%。
- 注错集上 11 字以上召回接近 0：整段一处编辑只到 24 个字母，词图敲错边只管敲错后仍是合法音节的。

## 做掉的两步

**原样成词保护**（`viterbi::typed_word_reach`，`TypoCosts::protected_extra` 4）：一条敲错边整个落在按敲的原样读出的多音节词里面时多扣一份。
第一版按位置保护（位置被原样词盖住就扣），`meiganxi` 的 没关系 被原样词 美感 拦住，改成「整条边落在里面」才拦。3 到 100 结果几乎一样。

**整句接上文**（`sentence::Search::initial`、`viterbi::initial_step`、`INITIAL_CONTEXT_WEIGHT` 0.5）：第一个词按「接着上文」与「句首」各半混。
全按接续算（权重 1）分段评测最高（53.9%），但回放词级掉 13 条：`dizhi` 出 的只、`danqian` 出 但前——静态与个人二元里「前词 → 的」攒得最多，
压过没见过接续的实词。个人部分也要混：只混静态时回放 5228，两边都混 5246。

## 再加两步（同日）

头两步合起来只有一个点上下，接着找大头。小旋钮都试了：回退换成按前词定（绝对折扣 + 接续概率）干净集 +0.8、回放词 −12，没采用；
词库兜底扣分 0 / −2 / −6 平；单字额外代价 1 起掉。留下来的是下面两个。

**每词代价**（`sentence::WORD_PENALTY` 1，`Interpolation::word_penalty`，`--tune word=`）：路径上每个词扣 1。二元模型把句子拆得越碎越容易碰上见过的高频接续，
几个单字会压过整词（笔给 压 笔记、点是 压 电视）。0.5 / 1 / 1.5 在全部尺子上都是正的，回放词 5349 / 5372 / 5387，留出学后 61.6% / 61.1% / 60.7%，取 1。

**从用户自己的文本学**（`Engine::learn_text`，CLI `--learn-text <文件>...`）：按语言模型切词、逐词记个人 n-gram 的转移，别的不动。
留出法：`docs/` 52 个文件里学 42 个、测另外 10 个，测的句子去掉在学的文本里原样出现过的，剩 1487 句：

| 配置 | 整句首选 | 字准确率 |
|---|---|---|
| 改前，冷 | 23.2% | 69.5% |
| 现在，冷 | 25.1% | 70.9% |
| 现在，学了那 42 个文件 | 61.1% | 89.9% |
| 改前，冷，开本地模型 | 26.7% | 72.3% |
| 现在，学了 + 本地模型 | 62.9% | 90.4% |

学了之后 16–20 字的句子首选 40%（冷的时候是 0%）。同一个人同一个题目的文本自相似度高，换个题目收益会小；个人插值封顶 0.5 保着没见过的话。
学完全部文档再回放真实日志：词 5317 → 5304，基本不动。壳里还没有入口（见 todo）。

四步合起来的回放（日志又长了些，词 5813）：词 5299 → 5372（91.2% → 92.4%），当时纠错生效 81 条仍纠 80 条不变。
整句一栏 213 → 175 不作数：逐条看过新增的没命中，「选了」的是 本的 / 点给 / 掉用 / 发不 / 版本好，现在出的是 本地 / 点击 / 调用 / 发布 / 版本号。
干净集 27.6% / 71.6% → 29.4% / 73.1%，分段输入 51.8% / 73.2% → 54.4% / 75.1%，注错集 14.7% → 15.7%。

## 真 k-best + 两轮重排（同日）

诊断里那条「给神经重排的 k 条路径只在句尾不同」修掉了。词图上每个节点留前 k 种走法（`viterbi::Arrival`：累计分 + 前驱下标 + 接的是前驱的第几种走法），
终点上全部节点的全部走法一起排、回溯、按文本去重。二元转移每个前驱只算一次，几种走法共用；只要一条时与只留最优回指逐位相同（干净集 29.4% / 73.1% 不变）。
路径数跟音节数走：每个音节 2 条，6 起、24 封顶。第二轮把各条路径相对词级最优路径净赚、互不重叠的替换拼成一条新路径再打一次分（`rescoring/combination.rs`）。

11–20 字的 1558 句，开本地模型（不开 11.7% / 74.7%）：

| 路径数 | 只第一轮 | 加第二轮 |
|---|---|---|
| 6（旧的假 k-best 约 12%） | 19.9% / 79.1% | 20.3% / 79.4% |
| 12 | 22.0% / 80.4% | 22.7% / 80.9% |
| 24 | 23.5% / 81.4% | 24.1% / 81.8% |

全集 9526 句开本地模型：早上 32.1% → 现在 42.0% / 80.5%（1–5 字 53.0%、6–10 字 37.7%、11–15 字 24.6%、16–20 字 21.6%；不开模型 29.4% / 73.1%）。
留出集学了个人文本再开模型：62.9% / 90.4% → 68.9% / 92.3%，16–20 字 51.9%。
模型权重 λ：冷启动 0.75 更好（43.3%），学了个人文本之后 0.5 更好（68.9% 对 67.1%），用户都有个人数据，保持 0.5。

代价：同步评测每句平均 135 ms（最慢 2.9 s，含一次查询里几遍整句转换的全部打分）；壳里是异步的，一次请求 12–24 条文本。
按键路径不开模型每键 2.6 ms 不变；异步开着时词图要留 24 种走法，每键 3.9 ms，120 键的长句最慢一键 14.6 ms（其中 parse 9 ms 是老问题）。
Windows 是 CPU 推理，24 条一批要几百毫秒，待真机看要不要把封顶降到 12。

上文权重扫描（分段首选 / 回放词，个人部分只按上文算的那一版）：0 → 52.3% / 5212，0.2 → 53.4% / 5222，0.5 → 53.7% / 5228，0.7 → 53.8% / 5224，1 → 53.9% / 5216。

## 整句读应用前文（2026-09-22）

以前整句只按**上屏链**接上文：链是我们自己上屏的最近两个词，标点、透传、切应用都打断它。
回消息、挪了光标之后接着打、粘贴之后接着打这三种场合链是空的，整句把句子当句首算，明显比 mac 自带输入法差。
应用光标前文其实早就进了 Core，但只给神经重打分看。这次把它变成一等的上文来源。

**取舍规则**（`engine/surrounding/`）：链上有词就用链，链是空的才用应用前文，壳给不出前文才当句首。
链上有词说明光标就在我们刚上屏的词后面，那个词是用户亲手选的、还带音节，比从文本切出来的准；
而且壳只在一段组句起头读一次前文，这段里后来上屏的词不在前文里，那时改用前文反而会把刚选的词丢掉。
前文按末尾**连续的汉字**切（遇标点 / 换行 / 字母数字就断），`segment_text` 出最后两个词存成 `SurroundingBefore`，
只在壳送来新文本时切一次，不是每键都切。学习记的转移仍只看上屏链，不拿别人的话喂个人 n-gram。

**壳侧**：macOS 以前只在「有本地整句模型或模型加载中」时才读前文，现在无条件在组句第一键读（Secure Input 仍不读）；
Windows DLL 与 Linux IBus / Fcitx5 本来就每段组句都送，Server 收到 `Surrounding` 后改成重排候选并重画
（前文是第一键之后才到的，第一帧按「没有上文」画过了）。读多少字仍是 `RESCORE_CONTEXT_CHARS` 64。

**数字**（同一份冻结句子集 9808 句，分段 `--eval-chunk 2` 共 23010 段；`--eval-context app` 是新加的模式：
前面各段的原文只经应用前文接口给引擎、上屏链保持空）：

| 组 | 首选 | 字准确率 |
| --- | --- | --- |
| 改前 分段 2 词（上文走上屏链） | 52.3% | 73.5% |
| 改前 分段 2 词 + `--eval-context app` | 50.5% | 72.3% |
| 改后 分段 2 词 + `--eval-context app` | 52.3% | 73.5% |

改前 app 那组等于「上文没用上」，改后与走上屏链的那组**逐位相同**：应用前文这条路已经和自己上屏的词一样管用。
干净集（27.5% / 71.3%）与分段集（52.3% / 73.5%）改前改后不变，回放（词首选 92.4%、命中 8850 / 9575）逐字节相同，没有退步。

真实数据上的一个翻盘：光标前是「好的我做了」时 `ba` 的首选是 吧，没有前文时是 把（吧 掉到第三）。

## 多音字读音份额（2026-09-22）

**病**：语言模型只看字不看音。词库早就按读音分了词频（`dict.tsv`：没 mei 929226 / 没 mo 7315，会 hui 957453 / 会 kuai 1255，
了 le 5314932 / 了 liao 115477，大 da 644752 / 大 dai 9841，的 de 10189450 / 的 di 21162 …，全库 871 个多读音词），
可这些词一进模型，`P(没 | 上文)` 是两个读音合起来的那一份。结果 `mo` 的首选是 没，`kuai` 是 会，`huo` 是 和，`dai` 是 大，`di` 是 的——
全是拿常见读音的分去赢冷门读音的位置。

**药**（`sentence::ReadingShare`）：一个词按某个读音命中时减掉 `ln(该读音词频 / 该词全部读音词频之和)`，没(mo) 约 −4.85，单读音词 0。
表在装词库时扫一遍全部词库建好（主词库 + 附加词库 + 用户词，871 条，约 13 ms），装词库 / 换学习器时重建；用户词后来变了不重建——
每次上屏都重扫 9 万条词目太贵，而用户词零星几百条、词频也小，「这个词我常用」本来就该由 weight 与个人 n-gram 表达。

几个当时想清楚的取舍：

- **只在静态模型认得这个词时减**。模型不认识时走的是 `fallback_log_prob(词目词频)`，用的就是这条词目自己的词频，本来只算这一个读音，再减一次是扣两遍。
- **减在个人插值之后**（等价于把插值结果整个乘上份额）。个人 n-gram 也只认字不认音：只减静态那一份的话，用户打过几次 没(mei)，`mo` 的首选还是 没
  （实测：只减静态那一版，带用户数据的 `mo` / `di` / `dai` 首选一条都没动，回放整句 273、词 8864，两头都不如现在这版）。
- **不进 `static_score`**。神经重排算的是 `路径分 + λ·(神经分 − 静态分)`，而字级 Transformer 同样不认识读音；把份额算进静态分，等于让重排把它还回来。
- **不参与格子挑候选**（`span_candidates`）。那里用的 `m.frequency` 就是按读音分开的那一条（没(mo) 是 7 千不是 92 万），已经是对的，再扣一次就把冷门读音从词图里删掉了。
- **与 `penalty` 分开存**（`SpanWord::reading`）。`penalty` 是「猜用户敲错了」的代价，还牵着原样成词保护（`PROTECTED_MIN_COST` / `typed_word_reach`），两件事不能混。
- **封顶**。词库里有词频记成个位数的冷门读音，不封顶一条边能扣掉二三十分，比任何语言模型分都大。

**案例**（冷启动，单字候选）：`mo` 没 → 莫（没 掉出前六），`kuai` 会 → 快，`huo` 和 → 或，`dai` 大 → 带，`di` 的 → 迪，`liao` 了掉出前六。

**反例**（靠冷门读音成词的多字词，读音是整词的、份额是 1，全部不变）：`changjiang` 长江、`yinhang` 银行、`chongqing` 重庆、`xingma` 行吗、
`liaojie` 了解、`kuaiji` 会计、`hemu` 和睦、`meiguanxi` 没关系，改前改后都是首选。

**代价**：回放里 20 条整句退了，逐条看都是用户真的用冷门读音打的字（`jichu` 选 给出、`zhekuai` 选 这会、`daiam` 选 大啊、`dijie` 选 的家）。
词级那一侧有同输入串的选择加分（`choice_bonus` 按敲的那段字母记）能把它们救回来，整句这一侧没有对应的东西——
个人 n-gram 记的是词，不记读音。要根治得让学习侧也按读音记，那是另一件事。
另外词库自己的读音词频并不都准（长 chang 81856 比 zhang 130456 还少），好在这种偏差只值零点几分，压不动什么。

**耗时**：按键路径不变（70 键长句每键平均 753 / 765 / 767 µs → 763 / 742 / 745 µs，最慢 2.5 ms 上下，在噪声里）；
建表让启动多 9 ms（38 → 47 ms，装主词库与换学习器各建一次）。

## 试过不行的

- 束宽 8 → 16 → 32：逐位一样。每格候选 6 → 12：29.3% → 28.0%，**放宽搜索反而变差**，说明找到的是分更高的错路径，瓶颈在打分模型。
- 静态插值 λ：0.6–0.8 平，0.9 起掉（0.99 掉 5 个点），固定 λ 已在平台上，要换的是回退方式。
- `prefer_convertible` 放开到多一个音节的切分：`womenquxianwanba` 修好了，整体字准确率 −0.4（多切的读法没有长度先验，乱赢）。切分错只占 0.5%，排最后。

## 怎么复现

```bash
cargo build --release -p glimmer-cli
target/release/glimmer-cli --eval-text docs/design/*.md docs/notes/*.md docs/plan/*.md docs/user/**/*.md --eval-save /tmp/sentences.tsv --misses 0
target/release/glimmer-cli --eval-text /tmp/sentences.tsv --misses 0                       # 干净集，带句长分桶
target/release/glimmer-cli --eval-text /tmp/sentences.tsv --misses 0 --eval-chunk 2        # 分段输入
target/release/glimmer-cli --eval-text /tmp/sentences.tsv --misses 0 --eval-typos          # 注错集
target/release/glimmer-cli --eval-text /tmp/sentences.tsv --misses 0 --eval-chunk 2 --eval-context app   # 上文只经应用前文
target/release/glimmer-cli --eval-text /tmp/sentences.tsv --misses 0 --tune initial=0,protect=0,word=0   # 改前的行为
target/release/glimmer-cli --eval-text /tmp/sentences.tsv --misses 0 --tune reading=0                     # 关掉多音字读音份额
target/release/glimmer-cli --learn-text <学的文件>... --eval-text <留出的句子集> --misses 0                # 从文本学，留出法
```
